.. god i love rST's replacement text feature

I have found that, especially when working on a contribution to a larger pre-existing project,
I end up running into a situation where I have non-|gi|'d files
which either need to be in the project directory, or  at least are convenient to have right there.

Things like:

- compilation or language specific files (e.g. a python ``.venv``)
- project-specific IDE configuration (e.g. ``.vscode``)
- notes! often there's things i need to take notes about, e.g. steps I've tried while trying to get something stubborn to compile or while trying to reproduce a bug

I can't add them to the |gi|, since that also gets committed.
I can't exactly be submitting a "hey i fixed this bug" pull request that also has

.. code:: diff

   +/.vscode
   +/.venv

in it.

So, adding it to |gi| is clearly out.
At the same time it *really* would be nice to still be able to just ``git add .`` with impunity,
rather than having to dodge around the not-ignored-but-should-be files.

How I personally like to do gitignores
======================================

.. |macmbd| replace:: ``my-awesome-cmake-build-directory``

Anything generated by any of the following things should be in your project's |gi|:

- Any custom build scripts which are part of the project itself.
- The sample commands provided in the project's documentation, at your discretion.

  If your ``README`` has compilation instructions which use |macmbd| as the main/only example,
  it should be in your project's |gi|.

  If |macmbd| were only used in the instructions for compiling in some niche edge case
  (i.e. not likely to be hit by most users, but is explicitly suggested),
  use your discretion.

  If |macmbd| were just a placeholder example for how one might potentially specify a directory name,
  i.e. explicitly expected to be replaced with whatever directory the user actually wants,
  probably don't |gi| it.
- The **standard** tooling for the softwares (language, build tools, etc.) used by the project.
- The local config files written by an IDE (or other such program),
  but **only** if that IDE is explicitly required (i.e. your project has scripts/configs which **only** work with that IDE and you have no interest in supporting any others),
  or at minimum is at least explicitly suggested for use in your developer documentation (or implicitly suggested by way of e.g. providing relevant setup instructions).

  Even still, it's at your discretion whether to |gi| it (I personally likely still wouldn't).
  This point is moreso to emphasize the fact that, if there isn't an actual expectation that any contributors/developers be using a particular IDE, then a particular IDE's stuff
  **should not** be in |gi|, as contributors can and should be putting their IDE's files in |gie|.
